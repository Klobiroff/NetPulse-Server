# Безопасность

Сервер считает любого клиента недоверенным. Здесь перечислено, что он проверяет сам, что даёт шифрование транспорта и где проверки нужно добавить вам.

## Что защищено, а что нет

Версия 0.4 умеет шифровать и аутентифицировать весь UDP-поток между клиентом Unity и сервером. Защита работает против:

- прослушивания: наблюдатель в сети не видит ни AppId, ни токена, ни имён комнат, ни игровых данных;
- подделки, изменения и повтора пакетов, включая подтверждения и сообщения об отключении LiteNetLib;
- «человека посередине», потому что клиент закрепляет публичный ключ сервера;
- перехвата сессии с того же адреса и подмены адреса отправителя для усиления трафика;
- исчерпания процессора, памяти и слотов подключения до того, как клиент подтвердил свой адрес;
- злоупотреблений со стороны уже подключённого клиента: этим занимаются лимиты скорости и размеров.

Шифрование **не защищает от самого игрока**. Клиент работает на машине атакующего:

- Память процесса, ключи сессии и игровая логика там читаются и правятся. Шифрование не даёт посторонним читать и менять трафик, но не мешает игроку отправлять что угодно через настоящее зашифрованное соединение.
- Всё, от чего зависит честность игры, должен проверять сервер или плагин. Любое значение от клиента считайте недоверенным, шифрованное оно или нет.
- Секреты внутри сборки (`ConnectionKey`, `AppId`, предварительно разделённый ключ) можно извлечь. Обфускация этого не меняет, и NetPulse не выдаёт её за защиту. Публичный ключ сервера не секрет, но он должен быть настоящим: именно он останавливает «человека посередине».
- Транспорт не аутентифицирует игрока. Любой клиент, знающий публичный ключ сервера, пройдёт рукопожатие. Кто игрок, определяет плагин аутентификации.
- В 0.4 не входят: античит, аттестация сборки, соединение, переживающее смену адреса клиента (NAT rebinding по-прежнему обрывает соединение), взаимная аутентификация по ключу клиента и постквантовый обмен ключами.

## Ключ подключения, AppId и версия

Три значения решают, кто вообще может разговаривать с сервером:

- Ключ подключения (`NetPulse:ConnectionKey`) проверяет транспорт. Клиент с другим ключом соединения не получает.
- AppId (`NetPulse:AppId`) проверяется при аутентификации. Если он задан, клиент с другим значением получает `InvalidAppId`.
- Версия протокола проверяется там же, когда `NetPulse:AppVersionCheck` равен `true`. Несовпадение даёт `VersionMismatch`.

Все три значения поставляются внутри вашей игры, так что любой, кто распакует сборку, их прочитает. Они отсеивают посторонних клиентов и устаревшие сборки, но не доказывают, что клиент настоящий игрок. При включённом шифровании по сети они больше не идут открытым текстом.

Клиент, не прошедший проверку AppId или версии, остаётся подключённым, но неаутентифицированным, и на все остальные операции сервер отвечает `NotAuthenticated`.

## Шифрование транспорта

`NetPulse:Encryption:Mode` определяет, кого принимает сервер:

| Режим | Поведение |
|---|---|
| `Disabled` (по умолчанию) | Слой шифрования не устанавливается. Формат на проводе и накладные расходы на пакет в точности как в версии 0.3. |
| `Optional` | Подключаются и шифрованные, и открытые клиенты. Открытый пакет с адреса, у которого уже есть зашифрованная сессия, отбрасывается, поэтому открытый пакет нельзя подсунуть в шифрованное соединение. |
| `Required` | Подключаются только шифрованные клиенты. Любая открытая датаграмма отбрасывается без ответа. |

`Optional` нужен для миграции. Он не защитит клиента, который подключился открытым текстом, и позволяет атакующему вынудить к понижению клиента, готового работать без шифрования. Поэтому у клиента Unity нет режима «предпочтительно шифровать»: он либо `Off`, либо `Required`, а клиент `Required` никогда не отправляет и не принимает открытые пакеты. В продакшене используйте `Required`.

При `Optional` и `Required` сервер не запустится без корректного приватного ключа.

### Алгоритмы

На всех платформах один фиксированный набор алгоритмов, ничего не согласуется, поэтому атаке понижения нечего понижать:

- обмен ключами X25519 с аутентификацией сервера по его статическому ключу через шаблон Noise `NK` (`Noise_NK_25519_ChaChaPoly_SHA256`, а при заданном предварительно разделённом ключе `Noise_NKpsk0_25519_ChaChaPoly_SHA256`). Даёт аутентификацию сервера и прямую секретность (forward secrecy);
- записи защищаются ChaCha20-Poly1305 (RFC 8439), свой ключ на каждое направление;
- SHA-256 и HKDF для вывода ключей.

X25519 и ChaCha20-Poly1305 реализованы управляемым кодом в `NetPulse.Common`, потому что их версии из .NET недоступны в Mono и IL2CPP Unity. Они работают за постоянное время, без ветвлений и обращений к таблицам по секретным данным и без выделения памяти на пакет. Реализации проверены по векторам RFC 7748 и RFC 8439 и сравнением с независимыми реализациями. SHA-256, HMAC и генератор случайных чисел берутся из платформы.

### Ключи

Создайте ключ сервера один раз:

```bash
NetPulse.Server keygen --out server.key
```

Команда пишет приватный ключ в файл (существующий файл она не перезапишет без `--force`) и печатает **публичный** ключ в Base64. Публичный ключ вставьте в настройки Unity ([Подключение](../unity/connecting.md#encryption)). Приватный ключ сервер получает так:

```json
{
  "NetPulse": {
    "Encryption": {
      "Mode": "Required",
      "PrivateKeyFile": "server.key"
    }
  }
}
```

Либо ключ задаётся переменной окружения `NETPULSE_SERVER_PRIVATE_KEY`. Настраивайте что-то одно. Приватный ключ никогда не попадает в `appsettings.json`, в логи и в тексты ошибок. Не кладите файл в систему контроля версий и закройте его для всех, кроме учётной записи, под которой работает сервер. Относительный путь считается от папки с бинарником сервера.

Сервер закрывается при сбое (fail closed). Он отказывается запускаться, если режим `Optional` или `Required`, а ключ отсутствует, имеет неверный формат или задан дважды, а также если числовая настройка вне допустимого диапазона. Ротация ключа описана в разделе [Развёртывание](deployment.md#rotating-the-server-key).

### Предварительно разделённый ключ

`NetPulse:Encryption:PreSharedKey` (Base64, 32 байта) или `PreSharedKeyFile` добавляет в рукопожатие второй секрет. Клиент без такого же значения его не завершит. Значение должно быть и в сборке клиента, так что любой, кто его извлечёт, сможет им пользоваться: оно лишь отсеивает клиентов, не имеющих вашей сборки. Сервер с таким ключом принимает только клиентов, которые его используют.

### Как начинается соединение

1. Клиент вместо первого запроса подключения LiteNetLib отправляет запись `Init` с идентификатором ключа, сообщением Noise и дополнением.
2. Сервер отвечает короткой записью `Retry` с cookie: HMAC от адреса и порта отправителя. Обмена ключами он ещё не делает и состояния не хранит. Ответ всегда короче запроса, поэтому сервер нельзя использовать для усиления трафика на подменённый адрес.
3. Клиент повторяет `Init` с cookie. Только теперь сервер выполняет обмен ключами и отвечает вторым сообщением Noise. Повторный `Init` с тем же эфемерным ключом получает кэшированный ответ без новой работы.
4. Клиент отправляет запрос подключения LiteNetLib внутри первой зашифрованной записи. Сервер активирует сессию, получив первую корректную запись.

Ошибки молчаливые. Неверный ключ сервера, неверный предварительно разделённый ключ, повреждённое сообщение или неизвестный идентификатор ключа не получают ответа и увеличивают метрику, то есть у атакующего нет оракула. Клиент видит `SecureHandshakeTimeout`. Секрет cookie меняется каждые `CookieLifetimeMs`, принимаются текущий и предыдущий.

### Записи, повторы и смена ключей

После рукопожатия каждая датаграмма — запись с накладными расходами 26 байт: тип, эпоха ключа, 8-байтовый счётчик, зашифрованные данные и 16-байтовый тег. Внутри весь пакет LiteNetLib, включая заголовки, подтверждения и сообщения об отключении. Счётчик только растёт, а скользящее окно (`ReplayWindow`, по умолчанию 4096) отбрасывает дубликаты и слишком старые пакеты. Окно двигается только после проверки тега, поэтому подделка его не сдвинет. Изменение любого байта записи ломает проверку. Когда счётчик приближается к пределу, сессия закрывается.

Каждое направление меняет свой ключ независимо, после `RekeyAfterPackets` пакетов (1 000 000) или через `RekeyAfterMs` (10 минут), хэшированием старого ключа. Потерянные и опоздавшие пакеты по-прежнему расшифровываются, а старый ключ стирается, когда окно повторов уходит дальше.

`PaddingBlock` (по умолчанию 0, то есть выключено) дополняет каждую запись до кратной размеру блока длины, что скрывает от наблюдателя длину сообщений ценой трафика. Он уменьшает полезный размер пакета на величину до размера блока. Задавайте одинаковое значение на клиенте и на сервере.

### Сессии и перехват адреса

Сессии хранятся по адресу и порту. Новое рукопожатие с адреса, у которого есть работающая сессия, игнорируется, если эта сессия не молчала хотя бы `ReplaceIdleMs` (3 секунды). Замена сессии всегда сначала отключает пира LiteNetLib, привязанного к старой сессии, поэтому новая сессия никогда не наследует аутентифицированного пира: тот, кто занял адрес, должен пройти аутентификацию заново. Сессия удаляется при отключении её пира (через секунду, чтобы последние пакеты успели уйти) или после `SessionIdleTimeoutMs` без трафика.

### Что видят плагины

Плагину аутентификации передаются `AuthRequest.IsEncrypted` и `AuthRequest.ChannelBinding`. Привязка к каналу — это хэш рукопожатия Noise, 32 байта, уникальные для данного соединения. Токен, в который она включена, действителен только на этом соединении и не подойдёт для повтора на другом. `IActor.IsEncrypted` показывает плагинам комнаты, зашифровано ли соединение игрока.

### Метрики

| Метрика | Значение |
|---|---|
| `netpulse.handshakes_ok` | Активированные сессии |
| `netpulse.handshakes_failed` | Рукопожатия, не прошедшие проверку или с неизвестным ключом |
| `netpulse.handshakes_rate_limited` | Рукопожатия, отброшенные лимитом на адрес, бюджетом сервера или занятой сессией |
| `netpulse.cookies_sent` | Отправленные ответы `Retry` |
| `netpulse.decrypt_failures` | Записи, не прошедшие проверку |
| `netpulse.replays` | Корректные записи, которые уже встречались |
| `netpulse.rekeys` | Смены ключей, в обоих направлениях |
| `netpulse.plaintext_rejected` | Открытые датаграммы, отброшенные в режиме `Required` или с шифрованного адреса |

### Известные ограничения

- Датаграмма, которую слой отбрасывает, не проходит обычный путь LiteNetLib, а LiteNetLib 1.3.5 в этом случае не возвращает свой буфер в пул. Поток мусора стоит выделений памяти в потоке приёма. Объёмный флуд останавливайте на файрволе или выше по сети.
- Исходящий пакет, который слой не может зашифровать, например для адреса, чья сессия уже ушла, отбрасывается отправкой пустой датаграммы.
- Один обмен ключами стоит около 1 мс процессора в управляемом коде (три операции X25519 по около 0,3 мс), так что одно ядро проходит около 1000 рукопожатий в секунду. `MaxHandshakesPerSecond` ограничивает сумму; его значение 2000 по умолчанию — потолок для всей машины, а не обещание. Шифрование и расшифровка записи в 1000 байт вместе занимают около 12 микросекунд.

## Аутентификация

Без плагина аутентификации сервер принимает любого клиента, который прошёл проверки выше. Идентичностью становятся присланные клиентом `UserId` и `NickName`. Отсюда два следствия:

- Клиент может назвать любой `UserId`. Если вы используете `PlayerTtlMs`, чтобы игроки могли вернуться, другой клиент с тем же `UserId` займёт место неактивного игрока, если не включить `NetPulse:Security:RequireRejoinToken` (см. ниже).
- Никнейм остаётся всего лишь подписью. Не используйте его для прав доступа.

Чтобы аутентифицировать игроков, установите плагин с реализацией `IAuthPlugin` и укажите его имя в `NetPulse:Plugins:Auth`. Тогда сервер использует `UserId` и `NickName`, которые вернул плагин, и игнорирует клиентские. В репозитории есть `AuthSample`: он проверяет токены с HMAC-подписью или спрашивает ваш HTTP-сервис. См. [Аутентификация](../plugins/authentication.md).

Сервер закрывается при сбое (fail closed):

- Если `NetPulse:Plugins:Auth` задан, а плагин отсутствует, падает при загрузке или не предоставляет `IAuthPlugin`, сервер отказывается запускаться.
- Если плагин бросает исключение при проверке клиента, клиент получает `AuthenticationFailed`.
- Отклонённый клиент или клиент, превысивший `AuthTimeoutMs`, получает `AuthenticationFailed` и отключается примерно через четверть секунды.

Токены аутентификации никогда не пишутся в лог. Без шифрования они всё равно идут по сети открытым текстом, поэтому используйте быстро истекающие токены, например HMAC-токены AuthSample с коротким временем жизни, и никогда не передавайте пароль в качестве токена.

## Лимиты для подключённых клиентов

Лимиты лежат в `NetPulse:Security`. Значение `0` выключает лимит. Значения по умолчанию подобраны так, чтобы обычная игра их не задевала. Нарушение лимита считается в метрике, а запрос отклоняется или пир отключается, как указано.

| Ключ | По умолчанию | Что происходит при превышении |
|---|---|---|
| `MaxConnectionsPerIp` | `32` | Следующее подключение с адреса отклоняется. Игроки за одним NAT делят лимит. |
| `ConnectionAttemptsPerIpPerSecond` | `20` | Запросы подключения сверх скорости (допускается всплеск вдвое больше) отклоняются. |
| `HandshakesPerIpPerSecond` | `10` | Рукопожатия сверх скорости отбрасываются после проверки cookie. Только при шифровании. |
| `MaxHandshakesPerSecond` | `2000` | Общий бюджет сервера на обмен ключами. Только при шифровании. |
| `AuthDeadlineMs` | `10000` | Пир, не аутентифицировавшийся вовремя, отключается с причиной `AuthTimeout`. |
| `MaxAuthAttempts` | `5` | Больше стольких запросов аутентификации без успеха отключают пира с причиной `TooManyAuthAttempts`. |
| `MaxMessagesPerSecond` / `MessageBurst` | `1000` / `2000` | Token bucket на пира. Пир отключается с причиной `RateLimited`. |
| `MaxBytesPerSecond` / `ByteBurst` | `1048576` / `2097152` | Token bucket на пира в байтах сообщений. Отключение с причиной `RateLimited`. |
| `MaxMessageBytes` | `262144` | Сообщение больше отключает пира с причиной `RateLimited`. |
| `MaxUserIdLength` | `128` | `InvalidRequest`. |
| `MaxNickNameLength` | `64` | `InvalidRequest`. |
| `MaxAuthTokenLength` | `8192` | `InvalidRequest`. |
| `MaxRoomNameLength` | `128` | `InvalidRequest`. |
| `MaxPropertiesPerRoom` | `256` | `InvalidRequest`, если обновление свойств или параметры создания превысят лимит. |
| `MaxPropertyBytes` | `16384` | `InvalidRequest`, если одно сериализованное значение свойства больше. |
| `MaxCachedEventsPerRoom` | `4096` | `InvalidRequest` для события, которое при кэшировании превысило бы лимит. |
| `MaxTargetActors` | `256` | `InvalidRequest` для события, адресованного большему числу акторов. |
| `RequireRejoinToken` | `false` | См. ниже. |

Сервер отклоняет запрос, превышающий лимит, а не обрезает его. `UserId`, `NickName` и имена комнат не должны содержать управляющих символов. Текст от клиента очищается от управляющих символов перед записью в лог, так что клиент не может подделать строки лога.

Читатель, разбирающий входящие сообщения, сверяет каждую заявленную длину с реально имеющимися байтами до выделения памяти и ограничивает число вложенных контейнеров в одном сообщении значением 4096, так что маленький пакет не заставит сервер строить огромный граф объектов.

### Токены возврата

С `PlayerTtlMs` игрок, потерявший связь, какое-то время сохраняет место и может вернуться с тем же `UserId`. Без плагина аутентификации этот `UserId` — лишь то, что заявил клиент. Если `RequireRejoinToken` равен `true`, сервер выдаёт каждому игроку случайный токен при входе в комнату, меняет его при каждом входе, а клиент Unity предъявляет его при возвращении в ту же комнату. Клиент без действующего токена для этого места получает `Forbidden`. Токен хранится в памяти клиента, поэтому игрок, перезапустивший игру, на место не вернётся.

## Защита от флуда

У каждого пира может быть не больше `NetPulse:PeerQueueLimit` сообщений (по умолчанию 256), стоящих в очереди и ещё не обработанных. Счёт общий для лобби и комнаты. Когда пир превышает лимит, сервер отбрасывает сообщение и отключает пира с причиной `Overloaded`. Такие случаи считает метрика `netpulse.peers_overloaded`.

Вторая граница, `NetPulse:RoomQueueCapacity` (4096), ограничивает сообщения, ожидающие в одной комнате или в лобби. При переполнении сообщение отбрасывается, а отключается пир с наибольшим числом сообщений в очереди, и это может быть не тот, кто отправил. Внутренняя работа сервера, например таймеры и `Host.Enqueue`, в оба лимита не входит.

Что это покрывает, а что нет:

- Ограничивается работа, ожидающая в очереди, поэтому клиент, заваливающий медленную комнату, отключается раньше, чем очередь вырастет безгранично.
- Сообщения и байты в секунду ограничивают лимиты скорости и размера выше.
- Служебные пинги и запросы аутентификации очередей не проходят, но лимиты скорости их учитывают.
- `NetPulse:MaxConnections` ограничивает число подключённых пиров, а лимиты на адрес выше — то, сколько может занять один адрес. Поток пакетов, которые так и не подключаются, останавливайте на файрволе.

## Проверка владения

Сервер ведёт реестр сетевых объектов в каждой комнате и проверяет каждое сообщение, которое их касается. Отклонённое сообщение отбрасывается, отправитель получает `Forbidden` (или событие `ErrorInfo`, если у запроса не было идентификатора, не чаще раза в секунду), сервер пишет предупреждение с ограничением частоты, а `netpulse.ownership_violations` считает случай. Никого за это не отключают.

| Сообщение | Принимается, когда |
|---|---|
| Создание объекта (событие 240) | View id не меньше 1000, принадлежит отправителю (`viewId / 1000 == actorId`) и не занят. |
| Уничтожение объекта (событие 241) | Отправитель владеет объектом или является мастер-клиентом. Сценовые объекты уничтожать нельзя. |
| Синхронизация состояния (событие 243) | Отправитель — текущий владелец. |
| Установка мастер-синхропеременной (событие 245) | Отправитель — мастер-клиент. |
| Передача владения | Режим объекта это допускает: `Fixed` не меняется никогда; `Takeover` позволяет забрать любому; владелец или мастер назначают кого угодно; `Request` позволяет назначать только владельцу или мастеру. |
| Регистрация сценовых объектов | Отправитель — мастер-клиент. |
| RPC (событие 242) и сообщения (событие 244) | Принимаются всегда. Если это важно, проверяйте их в плагине. |

Сценовые объекты (view id от 1 до 999) принадлежат мастер-клиенту, пока мастер никому их не передал. Когда игрок уходит насовсем, он теряет объекты, которыми владеет в данный момент; его сценовые объекты возвращаются мастеру. Неактивный игрок (ждущий возвращения) сохраняет всё.

Плагин может добавить своё вето через `OnBeforeTransferOwnershipAsync`, см. [Хуки](../plugins/hooks.md).

## Зарезервированные события

Клиент может поднимать коды событий от 0 до 199 (ваши собственные события) и объектные события 240–245: создание, уничтожение, RPC, синхронизация состояния, сообщение и мастер-синхропеременная. Любой другой код зарезервирован за сервером, запрос завершается `Forbidden` с сообщением `Reserved event code`. Серверные события, которые получают клиенты, включают список комнат, уведомления о входе и выходе, изменения свойств, смену мастера и владельца и `ErrorInfo`. Полный список — в разделе [Коды и ключи](../reference/codes.md).

Плагины этим правилом не связаны: `Host.BroadcastEvent` может отправить любой код.

## Зарезервированные свойства

Четыре ключа свойств комнаты управляют самой комнатой, поэтому менять их может только мастер-клиент:

| Ключ | Что задаёт |
|---|---|
| `_isOpen` | Могут ли входить новые игроки. |
| `_isVisible` | Показывается ли комната в списке лобби. |
| `_maxPlayers` | Лимит игроков, ограничивается диапазоном 0–255. |
| `_scene` | Текущая сетевая сцена. Смена удаляет привязанные к сцене объекты. |

Не-мастер, включивший один из этих ключей в обновление свойств комнаты, получает `Forbidden`, и ничего не применяется. Свойства другого игрока может менять только мастер-клиент; свои — любой. Плагин может менять зарезервированные ключи через `Host.SetRoomProperties`, который эти проверки пропускает.

Любое другое свойство комнаты может записать любой клиент комнаты. Не храните там авторитетные значения вроде счёта или инвентаря, если не защитили их. Проще всего защитить плагином:

```csharp title="ProtectedKeysPlugin.cs"
using NetPulse.Plugins;

namespace ProtectedKeys;

public sealed class ProtectedKeysPlugin : RoomPlugin
{
    private const string ServerPrefix = "server_";

    public ProtectedKeysPlugin(IPluginHost host)
        : base(host)
    {
    }

    public override ValueTask OnBeforeSetPropertiesAsync(IBeforeSetPropertiesCallInfo info, CancellationToken ct)
    {
        foreach (var key in info.Properties.Keys)
        {
            if (key.StartsWith(ServerPrefix, StringComparison.Ordinal))
            {
                info.Fail($"Property '{key}' is read only");
                return default;
            }
        }

        info.Continue();
        return default;
    }
}
```

Ключи `server_*` плагин пишет сам через `Host.SetRoomProperties`, который через хук не проходит.

## Чек-лист

1. Создайте ключ сервера, поставьте `NetPulse:Encryption:Mode` в `Required` и внесите публичный ключ в настройки Unity.
2. Задайте `NetPulse:AppId` и оставьте `AppVersionCheck` включённой.
3. Настройте плагин аутентификации и короткоживущие токены. По возможности привяжите их к `ChannelBinding`.
4. Авторитетное состояние держите за плагином и проверяйте события в `OnRaiseEventAsync`.
5. Оставьте лимиты по умолчанию, пока не измерили причину их менять, и следите за `netpulse.peers_overloaded`, `netpulse.peers_rate_limited`, `netpulse.ownership_violations` и `netpulse.decrypt_failures`.
6. Открывайте только UDP-порт и по возможности ограничивайте его файрволом.

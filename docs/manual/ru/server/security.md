# Безопасность

Сервер считает любого клиента недоверенным. Здесь перечислено, что он проверяет сам и где проверки нужно добавить вам.

## Ключ подключения, AppId и версия

Три значения решают, кто вообще может разговаривать с сервером:

- Ключ подключения (`NetPulse:ConnectionKey`) проверяет транспорт. Клиент с другим ключом соединения не получает.
- AppId (`NetPulse:AppId`) проверяется при аутентификации. Если он задан, клиент с другим значением получает `InvalidAppId`.
- Версия протокола проверяется там же, когда `NetPulse:AppVersionCheck` равен `true`. Несовпадение даёт `VersionMismatch`.

Все три значения поставляются внутри вашей игры, так что любой, кто распакует сборку, их прочитает. Они отсеивают посторонних клиентов и устаревшие сборки, но не доказывают, что клиент настоящий игрок.

Клиент, не прошедший проверку AppId или версии, остаётся подключённым, но неаутентифицированным, и на все остальные операции сервер отвечает `NotAuthenticated`.

## Аутентификация

Без плагина аутентификации сервер принимает любого клиента, который прошёл проверки выше. Идентичностью становятся присланные клиентом `UserId` и `NickName`. Отсюда два следствия:

- Клиент может назвать любой `UserId`. Если вы используете `PlayerTtlMs`, чтобы игроки могли вернуться, другой клиент с тем же `UserId` займёт место неактивного игрока.
- Никнейм остаётся всего лишь подписью. Не используйте его для прав доступа.

Чтобы аутентифицировать игроков, установите плагин с реализацией `IAuthPlugin` и укажите его имя в `NetPulse:Plugins:Auth`. Тогда сервер использует `UserId` и `NickName`, которые вернул плагин, и игнорирует клиентские. В репозитории есть `AuthSample`: он проверяет токены с HMAC-подписью или спрашивает ваш HTTP-сервис. См. [Аутентификация](../plugins/authentication.md).

Сервер закрывается при сбое (fail closed):

- Если `NetPulse:Plugins:Auth` задан, а плагин отсутствует, падает при загрузке или не предоставляет `IAuthPlugin`, сервер отказывается запускаться.
- Если плагин бросает исключение при проверке клиента, клиент получает `AuthenticationFailed`.
- Отклонённый клиент или клиент, превысивший `AuthTimeoutMs`, получает `AuthenticationFailed` и отключается примерно через четверть секунды.

!!! warning "Трафик не шифруется"
    NetPulse не шифрует UDP-трафик. Токены аутентификации и игровые данные идут по сети открытым текстом. Используйте быстро истекающие токены, например HMAC-токены AuthSample с коротким временем жизни, и никогда не передавайте пароль в качестве токена.

## Защита от флуда

У каждого пира может быть не больше `NetPulse:PeerQueueLimit` сообщений (по умолчанию 256), стоящих в очереди и ещё не обработанных. Счёт общий для лобби и комнаты. Когда пир превышает лимит, сервер отбрасывает сообщение и отключает пира с причиной `Overloaded`. Такие случаи считает метрика `netpulse.peers_overloaded`.

Вторая граница, `NetPulse:RoomQueueCapacity` (4096), ограничивает сообщения, ожидающие в одной комнате или в лобби. При переполнении сообщение отбрасывается, а отключается пир с наибольшим числом сообщений в очереди, и это может быть не тот, кто отправил. Внутренняя работа сервера, например таймеры и `Host.Enqueue`, в оба лимита не входит.

Что это покрывает, а что нет:

- Ограничивается работа, ожидающая в очереди, поэтому клиент, заваливающий медленную комнату, отключается раньше, чем очередь вырастет безгранично.
- Сообщения в секунду и байты в секунду не ограничиваются. Быстрая комната, которая справляется, до лимита не доходит.
- Служебные пинги и запросы аутентификации очередей не проходят.
- `NetPulse:MaxConnections` ограничивает число подключённых пиров, но число попыток подключения с одного адреса не ограничено. Для этого используйте файрвол.

## Проверка владения {#ownership-validation}

Сервер хранит в каждой комнате реестр сетевых объектов и проверяет каждое сообщение, которое их касается. Отклонённое сообщение отбрасывается, отправитель получает `Forbidden` (или событие `ErrorInfo`, если у запроса не было идентификатора, не чаще раза в секунду), сервер пишет предупреждение с ограничением частоты, а `netpulse.ownership_violations` увеличивается. Никого за это не отключают.

| Сообщение | Принимается, когда |
|---|---|
| Создание объекта (событие 240) | View id не меньше 1000, принадлежит отправителю (`viewId / 1000 == actorId`) и ещё не занят. |
| Удаление объекта (событие 241) | Отправитель владеет объектом или является мастер-клиентом. Сценовые объекты удалять нельзя. |
| Синхронизация состояния (событие 243) | Отправитель является текущим владельцем. |
| Запись мастерской sync-переменной (событие 245) | Отправитель является мастер-клиентом. |
| Передача владения | Режим объекта это допускает: `Fixed` не меняется никогда; `Takeover` позволяет забрать объект любому; владелец или мастер могут назначить кого угодно; `Request` позволяет назначать только владельцу или мастеру. |
| Регистрация сценовых объектов | Отправитель является мастер-клиентом. |
| RPC (событие 242) и сообщения (событие 244) | Принимаются всегда. Если они важны, проверяйте их в плагине. |

Сценовые объекты (view id от 1 до 999) принадлежат мастер-клиенту, пока тот не назначит их кому-то. Когда игрок уходит окончательно, он теряет объекты, которыми владеет в этот момент, а его сценовые объекты возвращаются мастеру. Неактивный игрок (ждущий возвращения) сохраняет всё.

Плагин может добавить собственное вето через `OnBeforeTransferOwnershipAsync`, см. [Хуки](../plugins/hooks.md).

## Зарезервированные события

Клиент может отправлять коды событий от 0 до 199 (ваши собственные события) и объектные события с 240 по 245: создание, удаление, RPC, синхронизация состояния, сообщение и мастерская sync-переменная. Любой другой код зарезервирован за сервером, и запрос завершается `Forbidden` с сообщением `Reserved event code`. Серверные события, которые получают клиенты, включают список комнат, уведомления о входе и выходе, изменения свойств, смену мастера и владельца и `ErrorInfo`. Полный список в разделе [Коды и ключи](../reference/codes.md).

На плагины это правило не распространяется: `Host.BroadcastEvent` может отправить любой код.

## Зарезервированные свойства {#reserved-properties}

Четыре ключа свойств комнаты управляют самой комнатой, поэтому менять их может только мастер-клиент:

| Ключ | Что задаёт |
|---|---|
| `_isOpen` | Могут ли входить новые игроки. |
| `_isVisible` | Показывается ли комната в списке лобби. |
| `_maxPlayers` | Лимит игроков, ограничивается диапазоном от 0 до 255. |
| `_scene` | Текущая сетевая сцена. Её смена удаляет объекты, привязанные к сцене. |

Если не мастер включает один из этих ключей в обновление свойств комнаты, он получает `Forbidden`, и ничего не применяется. Чужие свойства игрока может менять только мастер-клиент, а свои свойства может менять каждый. Плагин может менять зарезервированные ключи через `Host.SetRoomProperties`, который эти проверки пропускает.

Любое другое свойство комнаты может записать любой клиент в комнате. Не храните там авторитетные значения вроде счёта или инвентаря, если не защитили их. Проще всего защитить их плагином:

```csharp title="ProtectedKeysPlugin.cs"
using NetPulse.Plugins;

namespace ProtectedKeys;

public sealed class ProtectedKeysPlugin : RoomPlugin
{
    private const string ServerPrefix = "server_";

    public ProtectedKeysPlugin(IPluginHost host)
        : base(host)
    {
    }

    public override ValueTask OnBeforeSetPropertiesAsync(IBeforeSetPropertiesCallInfo info, CancellationToken ct)
    {
        foreach (var key in info.Properties.Keys)
        {
            if (key.StartsWith(ServerPrefix, StringComparison.Ordinal))
            {
                info.Fail($"Property '{key}' is read only");
                return default;
            }
        }

        info.Continue();
        return default;
    }
}
```

Сам плагин записывает ключи `server_*` через `Host.SetRoomProperties`, а этот вызов хук не проходит.

## Контрольный список

1. Задайте `NetPulse:AppId` и оставьте `AppVersionCheck` включённой.
2. Настройте плагин аутентификации и токены с коротким сроком жизни.
3. Держите авторитетное состояние за плагином и проверяйте события в `OnRaiseEventAsync`.
4. Оставьте стандартные лимиты флуда, если нет измерений, оправдывающих изменение, и следите за `netpulse.peers_overloaded` и `netpulse.ownership_violations`.
5. Открывайте только UDP-порт и ограничивайте его файрволом, где можно.
